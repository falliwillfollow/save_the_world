# n8n Discovery Lab Implementation

This document describes the local n8n implementation for CIaC discovery loops. It is intentionally separate from the sprint plan so the workflow can be reviewed, revised, or replaced without changing the core model.

## Purpose

The Discovery Lab is not a review queue. It is an automation loop that helps the model investigate itself:

1. Detect weak domains from world manifests, runtime bundles, capability warnings, and scenario failures.
2. Retrieve local context from patterns, module reports, runtime artifacts, scenario docs, and sprint plans.
3. Ask a local model, through Ollama, to propose structured interventions.
4. Validate the model output against CIaC schemas.
5. Run or queue simulations and comparisons.
6. Write candidate artifacts back into the repo for promotion, rejection, or branching.

CIaC remains the source of truth. n8n orchestrates retrieval, generation, validation, and artifact routing.

## CIaC-Initiated Research Loop

CIaC can now initiate a bounded research loop from the CLI:

```powershell
py -3.10 -m ciac research-loop examples/world_manifests/civic_floor_80_v0.world.json `
  --runtime examples/generated/micro_commons_runtime_bundle.json `
  --focus care_health `
  --discovery-output examples/discovery/research_loop.discovery.json `
  --candidate-output-dir candidate_interventions `
  --patch-output-dir patch_proposals `
  --output examples/discovery/research_loop.run.json
```

The command performs the conservative end-to-end handoff:

```text
DiscoveryLoopReport
  -> candidate selection from n8n webhook or deterministic seed candidates
  -> DiscoveryCandidateIntervention files
  -> PatchProposal files
  -> ResearchLoopRun summary
```

Use `--n8n-webhook <url>` when an n8n webhook workflow is ready to enrich or replace seed candidates. If the webhook fails, CIaC falls back to deterministic seed candidates unless `--no-seed-fallback` is set.

`PatchProposal` artifacts are written to `patch_proposals/`. They are implementable intent records, not automatic mutations. Promotion still requires validation, scenario comparison, and an explicit apply/promote step.

## Viewer-Driven Research

The 3D viewer can initiate the same loop through the Python viewer server:

```powershell
py -3.10 -m ciac viewer-server --port 8765
```

Open the 3D app, switch to Insight mode, and use the Research Lab panel. The panel posts the committed world state to:

`/api/research-loop`

The API writes the discovery report, candidate interventions, patch proposals, and a `ResearchLoopRun` summary, then returns those artifacts to the UI. When running through Vite, `viewer/world3d/vite.config.js` proxies `/api` to `http://127.0.0.1:8765`.

The live local stack routes the UI through n8n with:

`n8n/workflow_exports/ciac_research_loop_webhook.workflow.json`

`viewer-server` auto-detects local n8n at `http://127.0.0.1:5678` and uses the production webhook path when reachable:

`http://127.0.0.1:5678/webhook/ciac-research-loop`

You can still restart the viewer server with an explicit webhook URL:

```powershell
$env:CIAC_N8N_RESEARCH_WEBHOOK = "http://127.0.0.1:5678/webhook/ciac-research-loop"
py -3.10 -m ciac viewer-server --port 8765
```

Set `CIAC_N8N_RESEARCH_WEBHOOK=off` to force deterministic CIaC seed candidates.

When n8n participates, the `ResearchLoopRun` records:

```text
candidate_source: n8n_webhook
n8n.called: true
n8n.ok: true
n8n.trace_marker: n8n-rag-...
n8n.context_source_ids: [...]
```

The UI summary displays `n8n ok`, a trace marker, source count, and the n8n/Ollama brief. If n8n is unavailable or the webhook fails, CIaC falls back to deterministic seed candidates and records the n8n state or error in the run artifact.

## Added CIaC Artifacts

### DiscoveryLoopReport

Schema:

`schemas/discovery_loop_report.schema.json`

Generated by:

```powershell
py -3.10 -m ciac discovery-loop examples/world_manifests/civic_floor_80_v0.world.json `
  --runtime examples/generated/micro_commons_runtime_bundle.json `
  --focus all `
  --output examples/discovery/civic_floor_80_discovery_loop_v0.discovery.json
```

This report contains:

- `findings`: actionable weak domains such as care, governance, labor, mobility, water public health, and risk resilience.
- `retrieval_plan`: queries for the local RAG layer.
- `candidate_requests`: generation prompts for Ollama.
- `seed_candidates`: deterministic starter interventions that n8n can enrich or replace.
- `evaluation_contract`: metrics, scenarios, and rejection rules candidates must satisfy.
- `n8n_contract`: expected workflow nodes and artifact outputs.

### DiscoveryCandidateIntervention

Schema:

`schemas/discovery_candidate_intervention.schema.json`

Candidates are generated by n8n/Ollama or seeded by CIaC. Each candidate must declare:

- hypothesis
- intervention type
- target objects
- module references
- assumptions
- expected effects
- risk tradeoffs
- simulation hooks
- RAG context
- status

Candidates should be written to:

`candidate_interventions/*.json`

They should validate with:

```powershell
py -3.10 -m ciac validate candidate_interventions
```

### PatchProposal

Schema:

`schemas/patch_proposal.schema.json`

Generated by:

```powershell
py -3.10 -m ciac research-loop examples/world_manifests/civic_floor_80_v0.world.json `
  --runtime examples/generated/micro_commons_runtime_bundle.json `
  --focus care_health
```

Patch proposals declare:

- source candidate
- target artifact and change type
- provisional model changes
- simulation checks
- acceptance tests
- validation warnings or blockers

They should validate with:

```powershell
py -3.10 -m ciac validate patch_proposals
```

### ResearchLoopRun

Schema:

`schemas/research_loop_run.schema.json`

This is the orchestration record for a CIaC-initiated loop. It captures the discovery report path, candidate source, written candidate artifacts, written patch proposals, n8n webhook status, and next actions.


## Recommended Local n8n Stack

Use n8n as the orchestrator with local services:

- n8n desktop, Docker, or local npm install
- Ollama for local chat and embeddings
- A local vector store supported by the n8n AI nodes
- CIaC repo mounted as the working directory

Environment variables:

```text
CIAC_REPO_ROOT=D:\Projects\CIaC
CIAC_PYTHON=py -3.10
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_DOCKER_BASE_URL=http://host.docker.internal:11434
CIAC_DISCOVERY_OUTPUT=examples/discovery
CIAC_CANDIDATE_OUTPUT=candidate_interventions
```

## Workflow Shape

Use `n8n/workflow_specs/discovery_lab_pipeline.md` as the working spec.

A minimal importable test-drive workflow is available at:

`n8n/workflow_exports/ciac_discovery_lab_test_drive.workflow.json`

A UI-driven webhook workflow is available at:

`n8n/workflow_exports/ciac_research_loop_webhook.workflow.json`

It calls the local CIaC discovery bridge over:

`http://host.docker.internal:8791/discovery-loop`

It calls local Ollama from Docker n8n over:

`http://host.docker.internal:11434/api/generate`

Current test-drive flow:

```text
Manual Trigger
  -> Set CIaC Inputs
  -> Call CIaC Discovery Bridge
  -> Ask Ollama for Discovery Brief
  -> Parse Discovery Brief
```

Current UI webhook flow:

```text
Viewer Research Lab
  -> /api/research-loop
  -> CIaC DiscoveryLoopReport
  -> n8n webhook receives the report
  -> n8n requests /research-context from the CIaC bridge
  -> CIaC returns local retrieval snippets and an Ollama prompt
  -> n8n calls local Ollama
  -> n8n normalizes DiscoveryCandidateIntervention JSON
  -> n8n returns candidate_interventions with source_ids and trace marker
  -> CIaC validates candidates and writes PatchProposal artifacts
  -> UI displays ResearchLoopRun status
```

The first test-drive model is `qwen3.5:9b`. In local testing, Ollama's `format` option returned an empty response for this model, so the workflow currently relies on a strict JSON-only prompt plus a parser node.

High-level flow:

```text
Manual Trigger / Webhook
  -> Execute Command: ciac discovery-loop
  -> Split findings
  -> RAG retrieve local context
  -> Ollama generate candidate JSON
  -> JSON repair / split
  -> Write candidate_interventions/*.json
  -> Execute Command: ciac validate candidate_interventions
  -> Execute simulation / comparison commands
  -> Write comparison artifact
  -> Notify / open issue only if blocked
```

## RAG Index

Index these local sources first:

- `patterns/`
- `docs/module_reports/`
- `docs/ciac_sprint_*.md`
- `docs/civic_floor_world_mvp.md`
- `examples/generated/*.json`
- `examples/world_manifests/*.json`
- `scenarios/`
- `schemas/`
- `n8n/workflow_specs/`

Chunk by semantic section, not arbitrary line count where possible. Preserve file path and heading metadata so generated candidates can cite `source_ids`.

## Candidate Generation Prompt Contract

The Ollama prompt should include:

- one `finding`
- retrieved context snippets
- the `evaluation_contract`
- the full `DiscoveryCandidateIntervention` schema

Required instruction:

```text
Return only valid JSON objects of kind DiscoveryCandidateIntervention.
Do not write prose outside JSON.
Do not claim safety, legality, medical validity, public-health approval, engineering validity, or resident consent.
Every assumption must be explicit.
Every new risk must include a mitigation.
Every candidate must include simulation_hooks.
```

## Promotion Rule

n8n may generate candidates, but it may not promote them directly.

Promotion requires a CIaC command or future promotion workflow that verifies:

- schema validity
- no hidden labor regression
- no survival-critical unmet demand regression
- scenario comparison is not worse than baseline
- capability warning is reduced or converted into a more specific unresolved assumption
